# Vora — Project Guide for Claude

This file is the entry point. It tells you how Vora is organized, links to deeper docs, and lists the small set of rules you must follow on every change.

## What Vora is

Vora is a self-hosted media server with a .NET backend (`Vora.Api`) and a React SPA (`Vora.Web`). It indexes a user's media library, surfaces it through a cinematic, template-themed client UI (Home, Library, Live TV, Discovery, etc.), and supports IPTV with DVR, multi-server clients, profiles, plugins, real-time updates over SignalR, and scheduled visual templates (e.g. a Thanksgiving look for a date range).

## Tech stack at a glance

- **Backend:** .NET 10, C#, minimal APIs (`Vora.Api`)
- **Database:** PostgreSQL with the `vector` extension, EF Core
- **Real-time:** SignalR hub at `/hubs/Vora`
- **Email:** MailKit SMTP, ASP.NET Core DataProtection for SMTP password encryption
- **Frontend:** React + TypeScript + Vite + Tailwind, axios, `react-router-dom`, `@microsoft/signalr`, `hls.js`, `react-rnd`
- **Containerization:** API always runs in Docker; FFmpeg lives inside the container
- **IDE:** Visual Studio 2026, single solution `Vora.slnx`

## Golden rules — apply on every change

These are project-wide. The deeper docs add their own rules; these never bend.

**Backend (C#)**

- Nullable reference types are **on**. Treat warnings as bugs. **Never** suppress with `!` or `#pragma`. Fix the null path.
- Async methods always use the `Async` suffix.
- The codebase is intentionally **comment-free**. Let names and structure carry meaning. XML doc comments are also off.
- `Vora.Domain` depends on nothing else in the solution (the base `Pgvector` value-type package is allowed for the `MediaItemEmbedding` entity, but the EF Core variant is not). `Vora.Application` depends only on `Vora.Domain` and `Vora.Plugins` — `Vora.Plugins` defines the provider contracts Application code consumes (`IMetadataProvider`, `IArtworkProvider`, `IMediaIngestionService`, etc.). Implementations of repository interfaces live in `Vora.Infrastructure`.
- Endpoints stay thin: parse → call manager/service → return. Heavy logic goes into a Manager/Service in `Vora.Application`.
- Claims access **always** goes through `Vora.Api/Extensions/AuthExtensions.cs` (`GetProfileId`, `GetAccountId`, `HasAllLibraryAccess`, …). Never call `user.FindFirst("...")` directly.
- HTTP clients use `IHttpClientFactory`. No static `HttpClient`.
- API responses must use View Models (`*VM`) or Response classes from `Vora.Application`. Never expose `Vora.Domain` entities through the API.
- DI registration goes in the matching helper inside `Vora.Api/Extensions/ServiceRegistrationExtensions.cs`. Never inline registration in `Program.cs`.
- Enums are serialized as **strings** at the HTTP boundary. The global `JsonStringEnumConverter` is registered in `AddVoraJsonOptions`. Don't add enum values that depend on integer ordinals; new enums work out of the box.

**Frontend (TypeScript / React)**

- TypeScript linter is strict. **Never** leave `any` or `unknown` in the code.
- **Never** use `alert()`, `confirm()`, or `prompt()`. Use the dialog system: `const dialog = useDialog(); await dialog.alert(...)`. See `docs/frontend-conventions.md`.
- Routing lives in `App.tsx`. State management: nothing formalized — ask before introducing Redux/Zustand/React Query.
- All API calls go through the per-domain services under `src/api/<Domain>/` (e.g. `api/Media/mediaService.ts`). Do not call axios directly from pages.
- localStorage keys are documented in `docs/auth-and-devices.md`. Don't invent new ones in a vacuum.
- **Colors come from tokens, not Tailwind palette.** Use `var(--vora-bg-canvas)`, `var(--vora-accent-500)`, etc. — never `bg-gray-900`, `text-orange-500`, `text-white`, `hover:bg-white/5`, a Tailwind `shadow-lg`, or a hex/rgba literal in a component. Shadows use `--vora-shadow-*`; tints and scrims are `color-mix()` of a token; a third party's mark (IMDb, Rotten Tomatoes, Last.fm…) keeps its owner's colour through a token declared beside `--vora-lastfm-red` in `styles/tokens.css`. Tokens are scoped by `data-vora-client="" ` (set on `MainLayout` and `AuthLayout`) and `data-vora-admin` (set on admin shell). New pages that live outside those wrappers should add `data-vora-client=""` themselves (see `ProfileSelectionPage`).
- **One media tile, one row, one detail hero.** Every poster/tile in the client is `components/Client/Primitives/MediaCard.tsx`; every horizontal row is `MediaRow.tsx`; every wrapping grid is `MediaGrid.tsx`; people are `PersonCard`/`CastRow`; trailers and extras are `VideoCard`; the top of a detail page is `DetailHero.tsx` (+ `HeroChip`), shared by the media details and discovery details pages. Don't hand-roll a card, a scroller, or a detail header. The client has **no in-page Back buttons** — navigation back is the browser's; don't add `onBack` to `DetailHero`/`ActorProfile` or a Back pill to a page. What shows under a tile comes from `utils/posterCaption.ts` keyed on the item's type — add a case there rather than passing bespoke subtitles.
- **Every drawing of a movie, show, season or episode offers the title menu.** Pass `menu={mediaMenuTarget(item, serverId, { onChanged })}` to its `MediaCard`, or wrap a hand-built row in `MediaMenuArea`. The menu's entries and dialogs come from `useMediaItemActions`, which the title page's "more" button uses too — add or change an action there, never in one of the two places. See `docs/frontend-client-ui.md` → The title menu.
- **Card and row sizes come from tokens, not literals.** `--vora-card-w-xs|sm|md|lg`, `--vora-card-min-w` (`--vora-card-min-w-xs` for `xs` grids), `--vora-card-gap`, `--vora-card-title-size`, `--vora-card-caption-size`, `--vora-person-w` (`--vora-person-w-sm` for the compact Cast & Crew row on details pages), `--vora-video-w`, `--vora-row-gutter` in `styles/tokens.css`. They're `rem`/`clamp()` so the whole client scales with the root font size and the viewport. Never size a tile in `px`.
- **Phone styles never change desktop.** Below 48rem the client and admin get a phone layout. Add `max-md:` variants (or `md:hidden` / `md:contents` elements, or the phone token block) next to the desktop classes; never edit a class desktop uses. See `docs/phone-layout.md`.
- **Hover follows the pointer, never the device.** `index.css` redefines Tailwind 4's `hover` variant as `&:hover` (Tailwind gates it on `(hover: hover)`, which a browser reporting a touch screen answers no even with a mouse, and every hover in the app went dead there). Don't remove it, and never show or hide a hover affordance with `hover:`/`any-hover:` media queries: each one tried lit every episode play button on such a computer. Prove a hover change in Edge through the DevTools protocol with touch emulated before pushing.
- **Modals must overlay the header.** The header is `z-[100]`. The `Modal` primitive defaults to `z-[200]`. Raw `<div className="fixed inset-0 …">` modal overlays must use `z-[200]` or higher.
- **Video player logic lives in `usePlaybackController`**, shared by the web chrome (`GlobalVideoPlayer` over `WebVideoEngine`) and Vora Desktop (`DesktopPlaybackHost` over `DesktopMpvEngine`). An engine only plays; a playback decision never goes in an engine or a chrome. See `docs/frontend-client-ui.md`.
- **Live permissions (Live TV / DVR) are refetched live**, not read from JWT alone — the JWT is stale after admin edits. See `LiveTvPlayer` for the `userService.getUserAccount()` refresh pattern.

**Build & run**

- The API **always** runs in Docker (FFmpeg is in the container). Don't try to run `Vora.Api` natively.
- Start everything from Visual Studio: set `docker-compose.dcproj` as the startup project and run it. If the UI isn't already up, `cd src/Vora.Web && npm run dev` first.

## Things to be careful about

- **Comments**: don't add them, even XML doc comments. If a method needs explanation, rename or restructure it.
- **Migrations**: never edit a checked-in migration. Add a new one via `add-migration FooName` in the Visual Studio Package Manager Console.
- **localStorage keys**: see `docs/auth-and-devices.md` — the canonical admin flag is `is_server_admin`, NOT `is_admin` (that key is dead).
- **Header conventions**: device headers are all `X-Vora-*` (Device-Id, Client, Device, Device-Type, OS). The frontend interceptor in `src/api/client.ts` sends them; the backend `DeviceTrackingMiddleware` reads them.
- **Six Labors licence**: ImageSharp 4 / ImageSharp.Drawing 3 fail a Release build without a licence. `sixlabors.lic` sits at the repo root, gitignored — **never commit it or paste its contents anywhere**. CI and image builds use the `SIXLABORS_LICENSE_KEY` secret (Actions and Dependabot). See `docs/architecture.md`.
- **A third-party image address in a response needs `[RemoteImage]`**: channel and station logos and podcast artwork are often `http://`, which a browser will not load into an HTTPS page. The web sends those through `/api/artwork/thumb` (`secureImageUrl`), and that anonymous route only fetches an address the server has itself written into a response, which is what the attribute records. Leave it off a new view model and its `http://` images 404 on HTTPS. In the web, wrap such an address in `secureImageUrl(url, kind)` wherever it becomes an `<img src>` or a `posterUrl`. See `docs/artwork-image-cache.md` → Third-party images over plain HTTP.
- **Brand assets**: `public/favicon.svg`, `public/vora-logo.svg`, `public/vora-mark.svg`. The chevron-V wordmark is gradient-driven (`--vora-accent-text` → `--vora-accent-500`), so the brand recolors per template. Don't replace these with raster art. The installed app's icons are the one raster exception: PNGs in `public/icons/`, drawn from their SVGs there, because Android needs PNGs (`docs/architecture.md`, Installing the web app).
- **DataProtection keys**: SMTP password is encrypted via ASP.NET Core DataProtection (`AddVoraEmail` in `ServiceRegistrationExtensions`). Keys persist to `StoragePaths:DataProtection` (default `<base>/DataProtectionKeys`). **Mount this directory as a Docker volume** — otherwise keys roll on every container rebuild and the saved SMTP password becomes undecryptable. See `docs/email.md`.
- **`StoragePaths:Subtitles`** holds subtitles Vora downloaded from a provider. **Unset resolves beside the other configured data directories** (the parent of `VideoThumbnails` / `CustomArtwork` / …) via `SubtitleStorePath.Resolve`, *not* to `AppContext.BaseDirectory` — in Docker that is `/app/subtitles`, inside the read-only image, and every download failed there *after* the provider had already spent a unit of the daily quota. It is **persistent and server-managed** — the media library is read-only, so nothing Vora fetches is written beside the video. Mount it (or leave it under the existing `./Vora-data:/app/data`) or downloaded subtitles vanish on a container rebuild. Distinct from the derived-VTT cache under `TranscoderTempDirectory/subcache/`, which is disposable.
- **An unset storage path must not land in the app folder**: in Docker that is `/app`, which the server's user cannot write to (only `/app/data` and `/transcode` are). Resolve **every** storage folder through `StorageRoots` — never `Path.Combine(AppContext.BaseDirectory, …)` inline — so an unset one goes beside the configured paths, or into `/app/data`. A new `StoragePaths` setting needs a `StorageRoots` method and an entry in `StorageRoots.All`, which is what the startup write check walks. Never create a folder in the constructor of a service other managers depend on without catching the failure — an unwritable thumbnails folder once broke every media and library page, and surfaced as "Media not found". See `docs/video-thumbnails.md` → Storage.
- **Storage paths added since the original deployment**: `StoragePaths:Logs` (file sink under `<base>/logs`, see `docs/logs.md`) and `StoragePaths:Backups` (zip backups under `<base>/backups`, see `docs/backups.md`). The default `docker-compose.yml` puts both under the existing `./Vora-data:/app/data` mount so they survive container rebuilds. The **resized artwork cache** adds no new path — it writes under the existing `StoragePaths:CustomArtwork` at `imagecache/` and self-bounds at 512 MB (see `docs/artwork-image-cache.md`).
- **Media Trash (soft-delete) is video-only**: when a video file disappears the `MediaItem` is stamped `MissingSince` and hidden from client reads rather than deleted; music `Track`s still hard-delete. Nightly auto-purge is gated on `ServerSetting.EnableTrashAutoPurge` + `MissingMediaRetentionDays`, and a purge archives per-profile ratings + watch-state into `PreservedUserMediaData` (keyed by `ContentIdentity.Compute`) so a later re-add restores them. See `docs/scanning-and-tasks.md` and `docs/auth-and-devices.md`.
- **A cover image is not a video track**: a file can carry its poster as an extra video stream, and FFmpeg picks the stream to decode by pixel count, so a large cover beats a 720p episode. A new FFmpeg call that decodes video from a library file **must** add `CoverImageStreams.ProbeIgnoreArgumentsAsync(path, …)` before `-i` (or map the stream explicitly, as the transcode does). The probe drops covers, but older rows remain, so choose or list `VideoTracks` through `CoverImageTracks.Without` / `MainVideoTrack`, never `FirstOrDefault()`. See `docs/video-thumbnails.md` → Cover images.
- **Scrub-bar thumbnails vs the artwork cache are different subsystems**: `docs/video-thumbnails.md` is per-video WebVTT sprite sheets for the scrub bar; `docs/artwork-image-cache.md` is the resized poster/still/backdrop cache + poster overlay badges. Don't conflate `IVideoThumbnailService` with `IArtworkThumbnailService`.
- **A library scan's unit scans AND enriches in ONE DI scope**: `ScanAndEnrichUnitAsync` resolves the scanner + metadata manager from the same scope so enrichment writes onto the rows the scan just created. **Never** enrich in a separate `DbContext` from the scan that created the rows — that concurrent-context clobber is what silently blanked season posters (`ProcessTvSeasonsAsync` writes season posters during the show refresh). Parallel units are safe because each gets its own scope; shared rows (actors/genres/companies/…) are serialized by the singleton `ReferenceWriteGate` in `MetadataMappingService`. See `docs/scanning-and-tasks.md`.
- **Plugin settings can be bootstrapped from env vars**: `Vora__PluginSettings__<pluginId>__<settingKey>` env vars are read by `PluginSettingsEnvSeeder` at startup. Seed-once semantics — DB values take precedence. Plugin id + setting key are validated against installed plugins; unknown keys are skipped with a warning. Values are redacted from logs. Full per-plugin matrix lives in the README. See `docs/plugins.md` for the implementation.
- **Every AI call goes through `IOpenAiClient`, and every vector carries its model**: the client is where the address (`AiConnection`, OpenAI unless `base_url` says otherwise), the monthly token limit, the guardrails and the usage log live. The "For You" rows and the nightly movie/show embeddings used to call OpenAI directly and skipped the limit; never add another direct call or a hard-coded `api.openai.com`. `MediaItemEmbeddings.Embedding` is `vector(1536)`: shorter vectors are zero-padded (cosine is unchanged), longer ones are refused. Each row records the embedding `Model`, searches only read the current model's rows, and a row with no model counts as `text-embedding-3-small` so existing servers are not read again. **Never compare vectors across models, and never drop the model filter from a vector search.** See `docs/ai-connection.md`.
- **Radarr/Sonarr calendar credentials are NOT in plugin settings**: as of the Request Server unification, `radarr_calendar` and `sonarr_calendar` providers have empty `GetSettingDefinitions()` and resolve credentials through `IRequestServerLookup`, which reads `RequestServer` rows where `ProvidesReleaseCalendar = true`. The Release Calendar admin page is now a toggle + a pointer to System Settings → Request Servers. Don't reintroduce URL/API-key fields on those plugins.
- **Profile-scoped overrides for plugin behavior**: where a plugin setting can legitimately differ per profile, prefer adding the field to `UserProfile` and reading it in the endpoint before falling back to the plugin's admin default. Example: `UserProfile.ShowtimesLocation` overrides `serpapi_theater.default_location` (see `Vora.Api/Endpoints/DiscoveryEndpoints.cs` for the precedence pattern).
- **Session output files are namespaced by filename, not by directory**: everything a stream session produces lands flat in `TranscoderTempDirectory` prefixed with the transcode key (`session.ExtraId ?? session.MediaItemId`) — `{key}.m3u8`, `{key}_{n}.ts`. `GET /api/streaming/hls/s/{token}/{fileName}` serves a file only when the name starts with the prefix its token signs, so a new artifact **must** be named with the prefix its URL's token signs, and must **not** end in `_<integer>` or `TryParseSegmentRequest` treats it as an HLS segment. See `docs/streaming.md`.
- **The stream decision is pinned by a matrix, so run it in full before touching a weight**: `tests/Vora.Application.Tests/Streaming/Matrix/` checks every combination of file, client, setting and profile against rules written from what a client can play. The everyday run is about 314,000 combinations; `VORA_STREAM_MATRIX=full` runs more than 12 million, and it has caught problems the smaller set missed. Facts the rules rest on: a client's detected output and the viewer's pick are **separate fields** (folding them on the client made a pick above detection impossible to honour); **a browser starts an MKV on its first audio stream, not the default-flagged one**, so the original file is only served to a client that cannot switch tracks when the wanted track is both; `Remux` is HLS and must say `hls` in `TargetContainer`, because the TV apps map `mp4` to an MP4 player; the **Bitrate profile does not prefer small** — it goes to a smaller version only when the larger one is over the bitrate or its video cannot play as it is; and video is copied into HLS only when the client's `hlsVideoCodecs` (or `HlsVideoCarriage`'s default for its device type) takes the codec. See `docs/track-selection.md`.
- **GPU flags come from the resolved accelerator, never hard-coded**: every FFmpeg caller (transcode, marker scan, thumbnails, DVR) resolves `HardwareAccelerationType` + `HardwareTranscodingDevice` through `IHardwareCapabilityService.ResolveAsync` and builds its flags with `HardwareArguments`. A hard-coded `-hwaccel cuda` is what made an Intel box hang playback: the GPU process died and the session waited forever. A GPU transcode that exits with an error now restarts on the CPU (`OnFFmpegExited` → `RetryOnCpuAsync`); keep that path working. Quick Sync and VAAPI can only be proven on real Intel/AMD hardware. See `docs/hardware-acceleration.md`.
- **Copied video is cut at the file's own keyframes, by the segment muxer**: a Remux (or any session that copies the video) gets a `SegmentPlan` from the file's index (`KeyframeIndex`: Matroska Cues or MP4 sample tables) and FFmpeg runs `-f segment -segment_times`, not the HLS muxer, because the HLS muxer counts 4 seconds from where each run started and a seek-restart then wrote segments that no longer matched the playlist. Launch a run only through `SegmentPlan.LaunchAt` (the 0.25 s seek lead, the 0.15 s cut lead and the constant `-output_ts_offset` are what make every restart write identical segments), and keep the `.part` → `.ts` publishing: the segment muxer writes in place, so a segment is only served once FFmpeg has listed it in `_ffmpeg_{key}.list`. `KeyframeSegmentFileTests` proves both with real FFmpeg (skipped without it). See `docs/streaming.md`.
- **Text subtitles come from their own route, never from `/start`**: the transcode emits `-sn` unconditionally, image subs burn into the video (unless a client that sends `rendersImageSubtitles: true` gets a Direct Play and draws them from the file; any remux or transcode still burns them in), and text subs are served by `GET /api/streaming/sessions/{sessionId}/subtitle/{trackId}.vtt` from a content-keyed cache at `{TranscoderTempDirectory}/subcache/{partId}_{trackId}_{fingerprint}.vtt`, warmed after a scan by `ISubtitlePreExtractionManager` (`ServerSetting.PreExtractSubtitlesOnScan`, default on, independent of thumbnails) and extracted on demand otherwise. The fingerprint (source size + mtime + stream index) lives in the **file name**, so a changed source is a miss by construction — never add an age- or size-based eviction, the cache is keep-forever by design. **Never put extraction back on the play path**: a large remux takes minutes and blocking `/start` timed the client out. `StartStreamResponse.SubtitleUrl` is kept on the DTO but always null. `MediaSubtitleTrack.StreamIndex` is the **absolute** stream index (`-map 0:N`), not the subtitle-relative one (`0:s:N`) — don't mix the two, and the `0:s:N` ordinal counts **container streams only**, so sidecar rows must be excluded before indexing. The image-codec list is duplicated in `Vora.Web/src/utils/subtitleKind.ts` because the client decides whether to restart the stream before asking the server anything; **`SubtitleCodecParityTests` fails if the two drift**, since a mismatch means a restart with no subtitle (or a doubled one). A track is embedded or **external** (`ExternalFilePath` set, a `.srt`/`.ass`/`.vtt` beside the video): the two reconcile separately — `SyncMediaTracksAsync` by stream index for embedded, `SyncExternalSubtitleTracksAsync` by path for sidecars — because an ffprobe pass reconciling both would delete every sidecar. See `docs/subtitles.md`.
- **`UserMediaState.IsPlayed` is derived from the ping, not sticky**: `WatchStateTransition.ResolveIsPlayed` clears it once a re-watch passes a 30s grace window, sets it past 90%, and otherwise leaves it. It used to be `IsPlayed || completed`, which could only ever go true — so re-watching a finished item stored a resume position that nothing surfaced (`inProgress` on the details page and the Continue Watching query both require `!IsPlayed`). The grace window exists because a ping can land at position 0 before the player has seeked to its resume point. It equals `MinimumResumeSeconds`: a ping before 30s saves no resume point, so a peek leaves no Resume button or Continue Watching tile, and a re-watch stopped before then leaves the item watched. Where Play on a show starts is the profile's `UpNextOrder` (in order, or where I left off), decided in one place, `EpisodeToPlay.PickAsync` (`docs/frontend-client-ui.md`).
- **Live TV and radio favorites are per profile**, in `ProfileChannelFavorites` keyed by playlist + external channel id, not in the per-device `IptvPrefsJson`. The existing prefs endpoints merge them in on GET and replace them on PUT (`IChannelFavoritesManager`); a PUT that leaves the favorites field out leaves favorites alone, so a settings screen that only edits providers must not send it. See `docs/iptv-and-dvr.md`.
- **NFO files and local images are opt-in per library, and a Fix match outranks them**: `MediaLibrary.LocalMetadataMode` and `PreferLocalArtwork` default to off, and with both off nothing in a media folder is read. `"Match"` in `LockedFields` (set by Fix match) is checked **before** an NFO is used, in the fetch service and in the scanner, because a forced refresh ignores ordinary field locks; don't add an NFO or scan path that skips it. Local images are **never copied**: artwork URLs hold `/api/artwork/local/{mediaItemId}/{fileName}?v=…` and `ILocalArtworkLocator` resolves that to a file only when the name is that title's own artwork, so don't store a media-folder path in a URL column or widen `LocalMediaAssets.IsArtworkName`. See `docs/local-metadata.md`.
- **Marker locks reuse `LockedFields`**: admin-manual marker edits are protected by adding the literal string `"Markers"` to `MediaItem.LockedFields` (the existing `LockableEntity` pattern). `MediaAnalyzerManager.RunMediaItemSilenceDetectionAsync` and `FinalizeSeasonMarkersAsync` both bail early on `AreMarkersLockedAsync` — this means library/per-item analyze and the season cluster snap all respect the lock. Admin "Analyze media" clicks still force-override the trigger gate but still honor the lock; admins must unlock first to re-detect. See `docs/analysis-and-markers.md`.
