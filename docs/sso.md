# Sign-in providers (SSO)

Vora is self-hosted and has no domain of its own, so every server is its own client of whatever identity provider its admin chooses (Authentik, Keycloak, Authelia, Pocket ID, Google, Microsoft Entra, any OpenID Connect server) or its own directory (LDAP: Active Directory, OpenLDAP, LLDAP, FreeIPA, the Authentik LDAP outpost). For OpenID Connect the admin registers Vora at the provider with a redirect address of their own server, then pastes the issuer, client id and secret into **Users & Access → Sign-in providers**; for LDAP they enter the directory's address and a read-only account (see **LDAP** below). Vora ships no client id and talks to no central service.

This page is the design and the server rules. The server side of the OpenID Connect sign-in is complete (data, rules, the redirect flow, the one-time code, the admin API), and so is LDAP (**LDAP** below) and the web app's side of both (see **The web app**); TV pairing is built on the server and the web, and the native apps follow in later PRs. Nothing changes for a server whose admin adds no provider. How tokens work is in [`docs/auth-tokens.md`](auth-tokens.md); registration modes and invitations are in [`docs/auth-and-devices.md`](auth-and-devices.md).

## What is stored

| Table | Holds |
| --- | --- |
| `AuthProviders` | One row per provider: `Type` (`Oidc` or `Ldap`), `Slug` (the address name in the redirect URI, unique), `DisplayName` (the button), `Enabled`, `IconUrl`, `SortOrder`, `Issuer`, `ClientId`, `ClientSecretCiphertext`, `Scopes` (must include `openid`), the claim names read for email, name and groups, the two policies below, `AllowedEmailDomains`, `RequiredGroup`, `AdminGroup`; an `Ldap` row also holds the `Ldap*` columns under **LDAP**. |
| `UserExternalIdentities` | A provider account linked to a user: `UserId`, `ProviderId`, `Subject` (the provider's permanent user id), the email seen when it was linked, `LinkedAt`, `LastSignInAt`. Unique on `(ProviderId, Subject)`; deleted with the user or the provider. |
| `Users.HasPassword` | `false` for an account that signs in only through a provider (it holds an unusable random hash). Setting a password, in account settings or through a reset, makes it `true`. |
| `AuthRefreshTokens.SignInMethod` | `Password` or `External`: how the session began. |
| `ServerSettings.PasswordSignInEnabled`, `PublicBaseUrl` | The password switch (on by default) and the server's public address. |

The client secret is stored as DataProtection ciphertext (`IAuthSecretProtector`, purpose `Vora.Auth.ProviderSecret.v1`), like the SMTP password, so it needs the same keys (`docs/email.md`). It is write-only: no endpoint returns it, the admin VM carries `hasSecret`, and an update that leaves `clientSecret` out keeps it (`clearClientSecret` removes it).

## Who may sign in, and what happens the first time

`ExternalSignInService.SignInAsync(providerId, claims, options)` takes the claims a provider vouched for (subject, email, whether the email is verified, name, groups) and answers `SignedIn`, `NeedsLinkConfirmation`, `NeedsInvitePin`, `NeedsCreateOrLink` or `Refused` with a reason. The decisions are a pure function, `ExternalSignInRules`, tested cell by cell. In order:

1. A provider that is turned off refuses everyone.
2. **`RequiredGroup`** (when set) and **`AllowedEmailDomains`** (when any) gate every sign-in, linked accounts included.
3. A **linked identity** (`provider + subject`) signs in. Sign-in matches the subject, never the email, so an email changed at the provider cannot move or hijack an account.
4. A person who proves a **local password** (`options.LinkTo`) links that account, whatever the policies say: the password is the proof.
5. An **email match** with an existing account follows the provider's `LinkByEmail`:
   - `Never`: refused, "sign in the way you did before and link this from Account settings".
   - Never on an **unverified email**, whatever the policy.
   - The account has a password: `Automatic` links; `ConfirmWithPassword` (the default) answers `NeedsLinkConfirmation` and links once the right password is given.
   - The account has **no password** and no linked provider (one an admin added without a password): it links on the first verified sign-in. One that already signs in through another provider links only under `Automatic`.
6. **No account**: the person is asked to create one or link an existing one (`NeedsCreateOrLink`, with `canCreateAccount` saying whether creating is allowed). Creating follows `NewUserPolicy`:
   - `ExistingOnly`: never.
   - `IdpDecides`: always (the provider is the gatekeeper, optionally narrowed by group or domain). An explicit choice, never the default.
   - `FollowRegistrationMode` (the **default**): `Disabled` refuses; `Simple` (Open) creates; `SecretWord` asks for the 4-digit invite PIN (`NeedsInvitePin`, used up only when the account is made); `Invitation` needs the per-email invitation token, valid, for the **verified** email the provider gave, and uses it up. A person holding such an invitation is not asked to choose between creating and linking.
   - A new account needs an email. A provider that sends none can still link an existing account by password.

An account made here is built by `IAuthManager.CreateExternalUserAsync`, the same code as registration, so it gets the same first profile and defaults, with no usable password. Nobody becomes an administrator through a provider unless the admin set **`AdminGroup`** and the person is in it: that promotes on sign-in (and rotates the security stamp, ending older tokens), and never demotes. First-run setup stays password-only and a provider can never claim the server.

## The password switch

`ServerSettings.PasswordSignInEnabled` is on by default and an admin must turn it off on purpose (`PUT /api/admin/auth-settings`, refused while no provider of any type, OpenID Connect or LDAP, is turned on). Off, **everyone except administrators** is refused a password sign-in (403 titled "Password sign-in is turned off", not 401, which clients read as an expired session). Admin accounts keep their passwords, so an admin can never lock themselves out and there is no recovery switch to build. Also off: registering with a password, and an admin adding an account with one (add it without a password). A refresh token from a **password** session stops working for a non-admin (the family is revoked); provider sessions keep refreshing. `POST /auth/login` verification and linking use the same lockout and rate limits (`docs/auth-tokens.md`). Directory (LDAP) passwords are not passwords kept here, so the switch does not touch them: a person signing in through a directory still works with it off.

## Linked sign-ins

`GET /api/auth/identities` lists the caller's linked providers and `DELETE /api/auth/identities/{id}` unlinks one, refused with 409 when it is the **last way in**: no password that works (`HasPassword`, and password sign-in on or the person an admin) and no other linked provider that is turned on. Removing a provider (`DELETE /api/admin/auth-providers/{id}`) is refused with 409 when accounts could then no longer sign in, unless `?force=true`.

## The one-time code

A finished provider sign-in hands the browser or app a code, never a token (a token in a URL ends up in history and logs). `IExternalSignInCodeStore` keeps 32 random bytes per code, hashed, in memory, for 60 seconds, single use. `POST /api/auth/external/exchange { code }` (anonymous, `AuthStrict`) trades it for the same `accessToken` a login gives plus a `refreshToken` recorded as an `External` session; a used, expired or unknown code is 401.

## Public address and the redirect URI

The address a provider must be told is `{base}/api/auth/oidc/{slug}/callback`. `{base}` is `ServerSettings.PublicBaseUrl`, else the email link address (`EmailPublicBaseUrl`), else the address the admin's browser used. The admin VM returns the exact `redirectUri` for the admin page to show with a copy button. It must match what is registered at the provider character for character, so set the public address when Vora is behind a reverse proxy.

## Admin API

Admin-only, under `/api/admin/auth-providers` (list, get, create, update, delete) and `/api/admin/auth-settings` (get, update `{ passwordSignInEnabled, publicBaseUrl }`). Anonymous `GET /api/auth/providers` lists what the login page needs: `{ providers: [{ id, slug, displayName, type, iconUrl }], passwordSignInEnabled, directorySignInEnabled, registrationMode }`: turned-on OpenID Connect providers only (a directory has no button; `directorySignInEnabled` says one is on) and nothing about their configuration. Admin **Add user** takes `ssoOnly: true` to add an account without a password, which links on the person's first verified provider sign-in.

## Backups

`settings.auth-providers` (the providers; secrets decrypt only with the matching DataProtection keys) and `users.external-identities` (the links; skipped for a user or provider the server lacks). See `docs/backups.md`.

## The redirect flow

Authorization code flow with PKCE (S256), always. The browser, not the app, talks to the provider, so it works with anything that speaks OpenID Connect.

1. `GET /api/auth/oidc/{slug}/start?returnTo=&invite=` (anonymous, `AuthBurst`). Reads the provider's discovery document (cached an hour), keeps a server-side record for ten minutes (a random `state`, a `nonce`, the PKCE verifier, the exact redirect URI, `returnTo`, the invite token), and answers 302 to the authorization endpoint. `returnTo` is kept only when it is a path on this server (starts with one `/`, no `//`, `\`, scheme or control character, 512 characters at most).
2. `GET /api/auth/oidc/{slug}/callback` takes `code`, `state`, `error`. The state works **once** and only for the provider it was made for. The server trades the code on the back channel (secret in the Basic header, or in the body for a provider that lists only `client_secret_post`; none for a public client), then validates the id token and reads the claims. Then it answers 302 to the web app (the public address):
   - `/login/external?code=…&returnTo=…`: signed in; trade the code at `POST /auth/external/exchange`.
   - `/login/external?pending=…`: a step is left (link with a password, the invite PIN, create or link, or a refusal). `GET /auth/external/pending/{handle}` says which (`outcome`, `refusal`, `message`, `canCreateAccount`, `providerName`, `email`), and `POST /auth/external/complete { handle, createAccount?, invitePin?, linkEmail?, linkPassword? }` takes the answer (`AuthStrict`): `SignedIn` with a `code`, or the next step. A handle lives ten minutes and dies after five wrong passwords or PINs.
   - `/login/external?error=…`: it ended at once. Codes: `provider_unavailable`, `discovery_failed`, `access_denied`, `provider_error`, `state_expired`, `token_exchange_failed`, `id_token_invalid`, `missing_subject`.
3. **Linking from Account settings**: `POST /api/auth/oidc/{slug}/link { returnTo? }` (signed in) returns `{ url }` for the page to open. The same callback then adds the provider to that account and answers 302 to `/account?linked={slug}` or `/account?linkError=…` (the codes above, plus `link_conflict` when the provider account already belongs to another account here, and `link_refused` for a group or domain limit).

The id token must pass: signature against the provider's published keys (RS, PS and ES algorithms only, never `none` or a shared secret; a key it has not seen triggers one key refresh, at most every 30 seconds), `iss` equal to the issuer entered, `aud` equal to the client id (and `azp` when there are several), expiry (two minutes of skew), and the `nonce` of this sign-in. Email, name and groups come from the claims named on the provider; when the token has no email, or no groups while a group is required, the user-info endpoint is asked (only for the same `sub`). The admin's **Test** button (`POST /api/admin/auth-providers/{id}/test`) fetches the discovery document and the keys and reports the endpoints and what to fix.

## The provider's address is admin-supplied

The issuer is typed by an admin and is often on the LAN, so private addresses are allowed here, unlike the image downloader's guard (`docs/artwork-image-cache.md`). What limits it: http and https only; **redirects are never followed** (a 3xx is an error); 10 seconds in all and 1 MB per answer; the discovery document must name the issuer entered, and none of its endpoints may drop from https to http (a secret would cross the network unprotected); an http issuer is allowed and logged as a warning. Secrets, tokens and codes are never logged, and the saved secret is read only to trade a code.

## The web app

What a server without a provider shows is unchanged. Everything below appears only once an admin turns a provider on.

- **Admin: Sign-in Providers** (`/admin/sign-in-providers`, `pages/Admin/SignInProvidersPage.tsx`, linked from Users & Access and in the sidebar and Cmd-K palette). Two cards on top: the public address (`PUT /admin/auth-settings`, with what providers are told today) and **Allow password sign-in** (on by default; its off state reads "Require SSO for everyone except admins"; turning it off asks first through the dialog system, and with no provider turned on the server's refusal is shown instead). Then the presets in two groups (OpenID Connect, Google, Microsoft; and LDAP directory, Active Directory, OpenLDAP/LLDAP/Authentik; `providerPresets.ts`) and one card per provider: the exact redirect address with **Copy** (a directory's card shows its host, encryption, service account and search base instead), the two policies in words, **Test connection** (`POST /admin/auth-providers/{id}/test`, run again straight after a save; a directory's shows what the search found), **Edit** and **Remove** (a 409 "would lock accounts out" is asked again and retried with `?force=true`).
- **The editor** (`components/Admin/SignIn/ProviderEditorModal.tsx`; the rules live in `providerDraft.ts`, which has no React in it). The client secret is write-only: a saved one shows only as "A secret is saved", an empty field sends no `clientSecret` (the server keeps it), a typed one replaces it and **Remove the saved secret** sends `clearClientSecret`. New people: *Follow the registration mode* (default), *The identity provider decides* (marked "Opens sign-up" with a warning that it works even when sign-ups are closed) and *Existing accounts only*. Existing accounts: *Ask for the account's password once* (default), *Link automatically*, *Never*. Allowed email domains and a required group are optional; **Make members of a group administrators** is a tick box, off by default, that reveals its group field. Claim names and the icon sit under *advanced*. The Microsoft preset's issuer holds a `<tenant-id>` placeholder that fails validation until it is replaced.
- **Sign-in page.** `LoginPage` reads `GET /auth/providers` (best effort: an older server, or an error, leaves the page as it was). Providers and password on: the form, an "or" divider, one **Continue with X** per provider (`components/Auth/SignInProviderButtons.tsx`, its icon from `iconUrl`). Password off: only the buttons and a small **Admin sign-in** link that reveals the form, since admins keep their passwords. When a directory is on (`directorySignInEnabled`) the field reads **Email or username** and takes any text, and the form stays even with password sign-in off, because directory people use it (a line says passwords kept on this server only work for admins). A 409 from the login (a step is left) goes to `/login/external?pending=…` (`pendingSignInHandle` in `utils/externalSignInMessages.ts`). The register page and **Add user** know about a directory too. A button navigates the browser to `GET /api/auth/oidc/{slug}/start` on the server the page probed.
- **`/login/external`** (`pages/Auth/ExternalSignInPage.tsx`, public). `?code=` is traded once at `POST /auth/external/exchange`, the account token is stored exactly as the password login stores it, and the person goes to the profile picker. `?pending=` reads `GET /auth/external/pending/{handle}` and shows the step it names: link with the local email and password, the invite PIN, or *Create a new account / I already have an account* (only *link* when `canCreateAccount` is false); answers go to `POST /auth/external/complete`, and a wrong password or PIN is said in words while the step stays. `?error=` and refusals are worded in `utils/externalSignInMessages.ts`, one sentence per code in this page.
- **Register page.** With providers, **Continue with X** sits beside the form and carries `?invite=` to the start call, so an invitation is accepted by the account whose verified email it names. With password sign-in off only the buttons show; in PIN mode a line says the PIN is asked after the provider.
- **Account settings: Linked sign-ins** (`components/Account/LinkedSignIns.tsx`): the linked providers, **Link X** (`POST /auth/oidc/{slug}/link`, then the browser goes to the returned `url`) and **Unlink**. Unlink is greyed with the reason when it is the last way in (no working password and no other provider), and the server's 409 is shown if it disagrees. `/account?linked=` and `?linkError=` are read once and cleared from the address.
- **Users & Access**: each account says how it signs in (`Password · Authentik`, or *Waiting for their first provider sign-in* for an account added without a password), from `UserVM.hasPassword` and `UserVM.signInProviders`. **Add user** offers *Sign in with a provider* (`ssoOnly`, no password) when a provider is on, and makes it the only choice while password sign-in is off. The sign-up card says provider sign-ins follow its setting.
- **Setup guide**: a **Sign-in** step after Sign-ups, skippable, that lists the providers turned on and opens the providers page in a new tab.

## LDAP

A second `AuthProvider` type behind the same table, rules engine, new-user policy, link-by-email policy and password switch. Values for each product are in [`docs/ldap-setup.md`](ldap-setup.md).

**Sign-in is search, then bind.** There is no button: the login form takes an email **or a username** in the same field (`POST /api/auth/login { email, password }`, shape unchanged for every client). `PasswordSignInService` runs: locked out, refuse; **local account first** (a local admin can always sign in, directory down or not); then each turned-on directory by `SortOrder`. For a directory (`NovellLdapDirectory`, `Novell.Directory.Ldap.NETStandard` 4.0.0, pure managed, no open advisory): bind as the service account, search the user base with the filter, take **exactly one** entry (two matches sign nobody in), then bind **as that entry's DN** with the typed password on a **new** connection. Vora never compares a password, and an empty password or an anonymous bind never counts. `{username}` is put in the filter after RFC 4515 escaping (`\ * ( )` and NUL); an empty name, one over 256 characters or one with a control character is refused before any network call. Overall 20 s, connect 8 s, search 10 s, referrals not followed. Wrong credentials, an unknown name and a directory that is down are all the same bare **401** to the caller (and because local is tried first, a down directory never blocks a local account); the reason goes to the log (never the name or the password) and to the admin's **Test**.

**TLS.** `LdapSecurity` is `Ldaps` (default, port 636), `StartTls` (389) or `None`. The certificate must chain to the system roots **or** to the optional pasted `LdapCaCertificatePem` (that one root, no revocation check) and **always match the host**: a name mismatch is refused whatever the authority. `None` is accepted only for a private-network host (loopback, RFC 1918, link-local, CGNAT, IPv6 ULA, `localhost`, a single-label name, `.local .lan .internal .home.arpa .localdomain`) and the admin page makes the admin confirm that passwords cross the network in the clear.

**Columns** on `AuthProviders`: `LdapHost`, `LdapPort`, `LdapSecurity`, `LdapCaCertificatePem`, `LdapBindDn`, `LdapBindPasswordCiphertext` (DataProtection like the OpenID Connect secret and write-only: `hasBindPassword` out, `ldapBindPassword` in, `clearLdapBindPassword` removes), `LdapUserBaseDn`, `LdapUserFilter` (holds `{username}`, brackets balanced), `LdapMailAttribute` (`mail`), `LdapDisplayNameAttribute` (`displayName`), `LdapUniqueIdAttribute` (`entryUUID`), `LdapGroupAttribute` (`memberOf`) and an optional group search `LdapGroupBaseDn` + `LdapGroupFilter` (holds `{dn}` or `{username}`; both or neither). Attribute names match `^[A-Za-z][A-Za-z0-9-]*(;[A-Za-z0-9-]+)?$`. Turning one on needs host, base and filter. `RequiredGroup`, `AllowedEmailDomains`, `AdminGroup` (opt-in, off by default) and both policies work as above.

**Claims** (`LdapClaimMapper`): the **subject** is the unique id (an `entryUUID` or `uuid`, or a 16-byte `objectGUID` shown as a GUID), else the lower-cased DN; the **email** is the mail attribute and counts as **verified** (the directory is the authority, so use `Automatic` linking only for a directory you control); **groups** are each `memberOf` value as the full DN **and** its first RDN value (`RequiredGroup` may be `staff` or the whole DN) plus the group search. **An entry with no mail is refused** (403 "Sign-in refused"): there are never email-less accounts.

**What the login answers.** 200 `AuthResponseDto` (the refresh session is `External`); 401 bare; 403 "Password sign-in is turned off" (a local non-admin, switch off); 403 "Sign-in refused" with a `detail` (no mail, not in the group, domain, provider off); **409 "More is needed to finish signing in"** with `pending` (a handle: ten minutes, five wrong answers) and `outcome` (`NeedsLinkConfirmation`, `NeedsInvitePin`, `NeedsCreateOrLink`). A person with no account yet always gets a 409 `NeedsCreateOrLink` first (`canCreateAccount` false with a refusal when registration is closed), the same screen as an OpenID Connect first sign-in; a directory mail that matches a local account follows `LinkByEmail` (`ConfirmWithPassword`: the local password once). Both finish through `GET /api/auth/external/pending/{handle}`, `POST /external/complete` and `POST /external/exchange`. After that the directory signs in at the login in one step. The login lockout (5 failures by the typed name) and the `AuthStrict` rate limit apply; a refusal after the directory accepted the password is not counted as a failure. Native TV apps cannot finish a 409 and show a generic failure: they use pairing (`docs/device-pairing.md`).

**Test** (`POST /api/admin/auth-providers/{id}/test`, answered by type) connects, binds the service account, runs the user filter for up to 50 entries and returns `LdapTestResultVM`: `ok`, `message`, `connected`, `serviceBound`, `entriesFound`, `searchLimited`, `entriesWithMail`, `entriesWithoutMail`, `entriesWithUniqueId`, `sampleDns` (three) and `warnings` (no encryption, anonymous search, entries without mail, no unique id). Tests: rules and fakes in `Vora.Application.Tests/Auth/Ldap`, endpoints in `LdapEndpointTests`, and `NovellLdapDirectoryTests` against a real OpenLDAP, skipped unless `VORA_TEST_LDAP` is set (`tests/Vora.Infrastructure.Tests/Ldap/README.md`).
